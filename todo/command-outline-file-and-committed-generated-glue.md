# A command outline file as the single authority, with committed generated glue

## Context

The Go side declares commands by calling registration functions at startup, with every fact about the CLI passed as
data inside code: the command name as a string, its description, flags built with functional options, effects class,
payload schema, and renderer. Handlers read flags untyped from `map[string]any` by string key
(`strictcli.Get[string](kw, "email")`), and each consumer wires its groups by hand (one `Register(app, ...)` function
per group, called from the app's constructor). Large consumers each built their own wrapper over the bare handler
shape (a typed `(payload, error)` wrapper, a command struct table, a group table), which shows the framework has a gap.

The shape was set while the Go implementation had to match the Python and TypeScript implementations through a shared
conformance suite (struct-tag handlers once existed in Go and were removed for parity; see CHANGELOG). Those
implementations are paused and the suite is deleted, so the Go side can be designed Go-first. Go has no decorators or
annotations, so declaring commands in code always means registration calls with data inside them; the fix is to move
the data out of code.

## Decisions already made by the owner

1. **Naming form, a hard error when the program is built:** every command path is the tool name, then zero or more
   nouns, then exactly one verb (`safegit commit`, `<tool> brevo contact add`). Group words are nouns by position.
2. **Outline file:** each tool has an outline file (TOML, separate from code) that is the single authority for its
   command tree. Each command entry holds its path, description, flags and arguments (types, required or optional,
   help text), and effects class. Help output and `help --json` derive from it; the committed help-document copies
   some projects keep (`.strictmetadata/.cli-schema/schema.json`) are deleted.
3. **Planned commands:** a command in the outline with no implementation is planned. `help` shows it marked planned
   and `help --json` carries a planned field; running it is refused with a specific message ("`<path>` is planned in
   the outline and not implemented yet"), distinct from an unknown command. Static analysis reports what is
   implemented and what is planned.
4. **Placement:** the outline dictates where each command's hand-written code lives (`brevo contact add` lives at
   `<root>/brevo/contact/add.go`); authors have no freedom of placement. Handler bodies are never generated.
5. **Generated glue, committed:** a generator writes all mechanical code from the outline (and the handler files' Go
   source): registration with the framework, the typed input struct of each command (from the outline's flags, so each
   flag is stated once), flag parsing into it, help text, effects class, the wiring of the program's entry point, the
   payload schema derived from the authored output type, and a per-command planned stub for each command whose handler
   file does not exist yet (committed beside the handlers, so writing a handler without regenerating fails to compile
   with "redeclared"). Authors write only the handler and its output type, in plain Go.
6. **The generator commits what it writes**, automatically, as an `Autogenerated: true` commit. There is no
   fingerprint, no freshness test, and no other machinery to detect stale glue: structural mismatches already fail to
   compile (a handler that no longer matches its generated input type, a stub colliding with a new handler).
7. **Built-in commands follow the form too**: `version`, `config path`, `config init`, `check`, `failing-checks` and
   any others are renamed to tool + nouns + verb (the treatment of `help` and `version`, which agents look for by
   name, is open below).
8. **Consumers migrate with a migration program**, and each project's own test suite judges success: the same tests
   pass before and after, with only the mapped renames changed in test files, and each program's help document
   compares equal through the rename mapping.

## Evidence

All in this repository's `experiments/` (scratch, not committed):

- `experiments/noun-verb-naming/`: scripts that build every family program and dump its command tree through
  `help --json` (or `--dump-schema` on older ones), and tally naming violations (`run-all.sh`, `out/tally.md`).
- `experiments/declaration-ladder/`: ten designs from typed flag handles up to an outline as an interface definition,
  with prototypes; `proto/check9/` is a working checker that, with `go/parser` and `go/types` only, verifies a
  handler's input struct against an outline and reports `field Email int must be Email string (outline flag
  --email)`.
- `experiments/declaration-cmpr/`: prototypes comparing build-time-only generation, committed typed stubs, and
  committed generated glue.
- `experiments/rung11/`: an end-to-end prototype of an outline with generated glue: generator, checker, runtime
  additions (`sc/`), a toy tool (`toy/`), a slice of a consumer's Brevo commands translated to an outline
  (`wwwslice/`), a synthetic tool at 325 commands and 52 nouns (`scale/`), a concurrency test, a bootstrap converter
  from `help --json` to an outline (`bootstrap/`), and the exact-form rename tally (`tally-exact/`). That prototype put
  the glue in a gitignored directory with a startup fingerprint; both were dropped by decisions 5 and 6, but its
  generator, checker, planned handling, naming validation, and measurements carry over.

Measured in that prototype: generation 61-66 ms on the toy tool and 157-161 ms warm (505 ms cold, mostly
`go list` plus `go/types`) at 325 commands; plain `go build` of the large tool 3.8 s; a full command run about 13 ms.
Payload schemas emitted as Go map literals cost about 37 KB of binary per command (30.3 MB against 18.3 MB when the
schemas are emitted as JSON text), so the generator must emit declarations as data, not code.

## Findings that shape the design

- **Outline location:** `cmd/<tool>/outline.toml` beside the main package is the natural place (the authored entry
  point can embed it; `go:embed` cannot reach `.strictmetadata/`). Several tools in one module: one directory per
  tool, `cmd/<tool>/{main.go, outline.toml, <commands root>/, <generated files>}`, no includes across outlines.
- **Generated input types need their own leaf package** (handlers import their input types and the wiring imports the
  handlers; one package would be an import cycle).
- **Package names:** the last noun with dashes removed; Go keywords get a fixed suffix (`type` becomes `typecmd`,
  `go` becomes `gocmd`, verified to build); the nouns `internal`, `testdata`, and `vendor` must be refused (Go treats
  those directories specially). Command words are kebab-case, so `_GOOS`, `_GOARCH`, and `_test` suffix rules can
  never fire on file names (verified).
- **Disjoint vocabularies:** a word is a noun or a verb within one tool, never both; the validator refuses
  violations with sentences such as `"list" is a verb in "contact list" and a noun in "list"; a word is a noun or a
  verb in one tool, never both`. Near-synonym verbs under one noun (`delete` and `purge`) can be refused too, but the
  classes must be narrow (`generate` and `build` are not synonyms; neither are `check` and `verify`).
- **git-style continuation commands collide with disjoint vocabularies:** renaming safegit's `merge-continue` to
  `merge continue` makes `merge` both a noun and a verb (likewise revert and cherry-pick); those need another design,
  such as a flag or a choice flag.
- **Planned refusal must happen during routing, before parsing and before consent** (in the prototype the
  consequential prompt fired first).
- **Dependencies passed through registration today** (standard input passed to four groups, a network transport to
  two, plus app-specific values in several consumers) need framework doors: strictcli owns the stdin and HTTP doors
  with test options to replace them, and app-specific values arrive as a typed dependencies value.
- **Exit codes:** 18 handler sites in the family return exit codes other than 0 and 1 (saferm, pgdesign, strictgo,
  selfdoc among them); the `(output, error)` handler shape needs a way to return a specific code.
- **selfdoc** should obtain each program's help document from strictcli (from the outline through strictcli's own
  schema code), not from committed copies.

## Open decisions

1. The outline's file name (`outline.toml` recommended).
2. The full TOML schema: nouns with help (every noun declared, unused nouns refused), commands, flags and arguments
   (types, presence, help, defaults, short forms, environment variables, choices, variadic arguments), constraints and
   update-of relations, effects, consequential, dry-run support, renderer presence, global flags, requirements,
   deprecated paths, and how provider-call declarations some consumers keep are carried (typed extension keys passed
   to an app hook recommended).
3. `cmd/<tool>/` for every tool, or the module root for single-tool modules (`cmd/<tool>/` recommended, uniform).
4. Where the generated files live and their reserved name pattern (one generated directory, or files with a reserved
   prefix beside the handlers, which the per-command stubs need).
5. The handler file shape: function name from the verb (`Add`), the context type per effects class (two types, or
   three adding a consequential context), the output type declared in the same file, an optional renderer, and how a
   specific exit code is returned.
6. Input type naming: one flat package with path-derived names (`inputs.BrevoContactAdd`) or one input package per
   noun.
7. Whether every non-test file under the commands root must be one command's handler (shared helpers moving to
   `internal/`), or one reserved helper file per package is allowed.
8. Verb authority: a closed family verb list in strictcli with narrow synonym classes (the family uses 153 distinct
   verbs, 87 of them once), or each outline declaring its verbs.
9. Dependencies: a typed third handler parameter when the outline declares them, or an accessor on the context.
10. Tests: external test packages beside the handlers, building the app through a generated test constructor.
11. The planned command's exit code (1 with its own sentence, or a dedicated code), whether `help --json`'s planned
    field bumps the help document's version, and how planned commands appear in MCP tool lists, `Call`, and
    test-coverage manifests.
12. The generator's command names (for example `strictcli generate <tool-dir>`, a static implemented and planned
    report, a help-document printer for selfdoc), all needing the owner's approval as names.
13. The new names of the built-in commands, and whether `help` and `version` keep their names as reserved exceptions.
14. Untyped payloads: a large consumer has 290 commands returning untyped payloads; real output structs, or a
    `strictcli.Document` type with an empty schema to start.
15. The redesign of git-style continuation commands (`merge-continue` and similar).

## Migration

- Bootstrap each program's first outline from its current `help --json` (the tally scripts capture every program;
  the prototype's converter does it, leaving help empty for new nouns).
- A migration program, run per project with a dry run first: find each command's handler (strictcli can report every
  registered handler's function and file, which covers every consumer's registration style uniformly), move it to
  its mandated file and rename it after the verb, rewrite literal-key flag reads into typed input fields (about 620
  reads family-wide), delete the old declaration code, rewrite command paths in tests from the rename mapping, and
  report what it could not do mechanically (helpers left unreachable in their old package, dependencies passed
  through registration, dynamic flag reads). It may change only command paths and result reads in test files; any
  other test change is flagged for review.
- Success is judged by each project's own tests (decision 8).
- Order: strictcli releases once at the end of its work; then rlsbl (its CI templates, release configuration, and
  dev-install change to run generation), then selfdoc, then the other consumers, smallest first.

## Affected areas

The Go API (commands, groups, flags, handler shape, contexts per effects class, stdin and HTTP doors), the outline
parser and validator, the generator, planned support in routing, help, `help --json`, MCP, and `Call`, the
construction-time naming check over the whole tree, the built-in commands' names, docs and quickstarts (which teach
`update-record` as the example command, 62 times in the behavior cases), migration scripts, and every consumer.

## Effort estimate

strictcli: about 6 to 8 agent-days (the prototype estimate, reduced by dropping the build wrapper, gitignored
directory, locked swap, and fingerprint). Consumers: from 1 to 3 hours for small programs up to 4 to 6 days for the
largest.
