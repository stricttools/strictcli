# A generator command group: declared outputs, an injected stamp, and a status command derived from generate

## Context

Several consumers of strictcli are generators: they read declarations and
write files that are committed into the repository (documentation pages,
changelog pages, workflow files, validators, data tables). Each one today
hand-rolls the same three things: a stamp line at the top of every written
file saying the file is generated and must not be edited, a freshness check
that regenerates in memory and compares against the tree, and the wording of
the remedy that tells a reader which source to edit and which command to run.
A fleet-wide survey found eleven different stamp wordings across five tools
and eight scripts, no shared freshness check, and freshness checks that
exist only for the tools that bothered to write one.

strictcli already owns the pieces this needs: every command declares an
effect class, a mutating command's file writes are recorded instead of
performed under the framework's dry run, checks are declared with tags and
purity, and machine-mode JSON output exists for every command.

## Problem

- Every generator invents its own stamp, so no reader or check can
  recognize generated files by one rule, and the remedy text in the stamp is
  typed by hand and is sometimes a command that does not exist.
- Every generator that wants a freshness check writes a second code path
  beside its generate path, and the two drift.
- Nothing stops a generator from writing a file it never declared, so the
  set of generated paths in a repository is known only by reading the tool.
- Consumers that want the repository's path declarations (which paths are
  generated, which are authored, which are append-only) to stay in step
  with the generator have to maintain that declaration by hand.

## Solution: a command group declared as a generator

A group option, for example `WithGenerator(...)` on the group, that makes the
framework enforce and provide the following at registration time and at run
time.

**Shape, enforced statically at registration:**

- The group has exactly two commands: `generate` and `status`. Any other
  command in the group is a registration-time error naming the rule.
- `generate` declares the mutating effect; `status` declares read-only and
  is pure, so it runs under every dry run and every pure-only check run.
- Both commands carry machine-mode JSON output.
- The group pre-declares its outputs (paths or patterns it writes) and the
  inputs it reads. A `generate` run that writes an undeclared path is a
  run-time refusal naming the path and the declaration to extend.

**The stamp, injected by the framework:**

- Every written file whose extension has a known comment syntax gets two
  leading lines, placed after any shebang or front-matter fence: the first
  reads "Code generated by TOOL VERSION from SOURCE. DO NOT EDIT." and the
  second reads "Regenerate: see the COMMAND group" where COMMAND is the group
  name, since the group predictably has both `generate` and `status`.
- Files without comment syntax (JSON) get a leading object with the fields
  `tool`, `version`, `source`, and `command`.
- The tool name and version come from the app registration, the source from
  the declared input the output derives from, and the command from the
  group, so nothing in the stamp is typed by a person.
- No timestamp is ever written into a stamp, because a byte comparison is
  the freshness check and a timestamp would make every regeneration a diff.
- The stamp form is chosen so that Go's own convention for generated files
  is matched on the first line, since GitHub and Go tooling recognize it.

**`status`, derived from `generate`:**

- The framework runs the group's `generate` handler under dry run, collects
  the recorded file writes, and compares each declared output against the
  tree, reporting each as fresh, stale, or missing, with a nonzero exit when
  any is stale or missing and the remedy naming the group.
- No second implementation exists in the consumer; `status` is what
  `generate` would have written.

**The repository's path declarations, rendered:**

- The group can render its declared outputs into the repository's path
  declaration directory under `.stricttools/` (the directory the release
  tooling owns for stating which paths are generated, authored, read-only,
  or append-only), marking its outputs as generated and read-only, so that
  declaration is derived from the writer rather than maintained by hand.

**Optional autocommit:**

- A hook point after a successful `generate` so a consumer can commit the
  written outputs through its commit tool with the trailer that exempts
  machine-made commits from changelog coverage. Off by default; the commit is
  an effect and is recorded under dry run like any other.

## Alternatives considered

- **A shared stamp library only**, with each consumer keeping its own
  freshness check. Cheaper, but leaves the second code path and the drift.
- **A freshness check library only**, with consumers passing a render
  function. Removes the drift but leaves stamps and declared outputs to
  convention.
- **Nothing in strictcli**, each consumer continues alone. The survey shows
  where that leads.

## Affected files

- `go/strictcli/strictcli.go`: group registration and the new group option;
  the registration-time shape checks.
- `go/strictcli/effects.go`: the recorded write set under dry run, exposed to
  the derived `status`.
- `go/strictcli/check.go` and `check_public.go`: if the derived `status` is
  also exposed as a check, tagged and pure.
- The machine-mode envelope for the `status` report.
- The Python and TypeScript implementations, in lockstep, since the three
  share one conformance corpus.
- Conformance cases for the registration refusals, the undeclared-write
  refusal, the stamp per extension, and the fresh, stale, and missing
  reports.

## Effort

Go implementation with conformance cases: about a week. Python and
TypeScript parity: about a week more. The stamp per extension and the JSON
form are the fiddly parts; the derived `status` is small once the recorded
write set is exposed.
